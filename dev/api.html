Instrumentation ​

Treebars.@progress Macro
julia
@progress [backend_or_node] [label] body

Instrument a loop, comprehension, map, block or expression while preserving its result. With no explicit backend or node, use Treebars.BACKEND[], whose default nothing disables progress.

A standalone @progress "label" inside a block marks a phase. All markers are prepared up front; a phase finishes at the next marker or block exit. Unentered phases become skipped. A phase that throws becomes failed and the exception is rethrown. Labels may be literal or interpolated strings, or conditionals choosing strings, evaluated before the plan begins.

Within the macro body, __progress__ denotes the active node. Plain for and Threads.@threads for loops inside it become counters too; nested loop counters are transient. Comprehensions and maps require explicit wrapping. The map form gives each item its own child. Lazy generators and filtered or multidimensional comprehensions are not supported as wrapped counters.

Nested @progress, Treebars.@progress and longer paths ending in Treebars are recognized; arbitrary aliases are not. Bare strings are not phase markers. Use with_progress to pass a node to an ordinary function.

source
Treebars.@phases Macro
julia
@phases body
@phases node body

Instrument each top-level statement of a block or loop body as a prepared phase, labeled with shortened statement source. Compound statements remain one phase. The node form is self-contained; the body-only form uses the active node inside @progress, or Treebars.BACKEND[] when standalone.

Statements share a scope across phases, but assignments do not escape the macro's try scope. Define a binding outside the block if it is needed later. Use explicit phase markers when labels should describe tasks rather than code.

source
Treebars.@with_progress Macro
julia
@with_progress phase body

Start a prepared phase, run body, and finalize it on completion. On an exception, fail the phase and rethrow. Inline expansion preserves return, break, continue and local-variable access in the surrounding scope. Use within with_prepared_phases so unentered phases are closed too. See with_prepared_progress for the function form.

source
Treebars.with_progress Function
julia
with_progress(f, kind::Symbol[, N]; description="Running...", kwargs...)
with_progress(f, parent::ProgressNode[, N]; description="Running...", transient=false, kwargs...)

Initialize a node, call f(node), and finalize it on completion or fail it on error. Return the callback's value. Return the node explicitly if the caller needs to inspect it afterwards.

Arguments follow initialize_progress!. N is a counter total, passed positionally or as a keyword, not both. transient=true detaches a finished child; a failed child remains. With parent=nothing, the callback receives nothing and still runs normally. Use update_progress! inside the callback to report a counter position or message.

source
Treebars.with_prepared_progress Function
julia
with_prepared_progress(f, phase)

Start a prepared phase, call f(phase), and finalize on completion or fail and rethrow on error. Return the callback's value. Pair with with_prepared_phases, which owns cleanup of unentered phases.

source
Treebars.with_prepared_phases Function
julia
with_prepared_phases(f, parent, descriptions; kwargs...)

Prepare pending children and call f(phases). An iterable supplies labels; a named tuple preserves its keys and uses string values as labels, otherwise the key's string. Keywords, including N and transient, pass to each prepare_progress! call. Return the callback's value.

Enter each reached phase through with_prepared_progress or @with_progress. On every exit, pending phases become skipped. On error, running phases are failed before the exception is rethrown. Repeated plans contribute counts to phase_overview.

source
Treebars.progress_map Function
julia
progress_map(f, parent, itrs...; description="Running...", transient=false, kwargs...)

Map the iterables, passing a progress child before each item's arguments: f(child, xs...). Return the mapped collection. The parent owns a map counter; description labels that counter and transient controls its lifetime. Iterables without a known length have an indeterminate counter.

Per-item children start without labels; give them a message or nested work. Keywords pass to their initialize_progress! calls. Report into the callback's child, not an enclosing macro's __progress__. With parent=nothing, the map still runs and children are nothing.

The macro form @progress [label] map(itrs...) do xs... supplies the child as its body's __progress__. Keywords on that map retain ordinary Julia map semantics; use the function form for child keywords.

Nodes and lifecycle ​

Treebars.ProgressNode Type
julia
ProgressNode{I,M,C}

A node with backend state, a parent and children. Obtain nodes through with_progress or with_prepared_phases; use the public lifecycle and query functions rather than mutating backend fields.

source
Treebars.StateProgress Type
julia
StateProgress

The thread-safe state backend selected by :state. It retains labels, counters, messages and lifecycle state for text, snapshot and web views. Query it through is_pending, is_running, is_finished, is_failed, is_skipped and is_reused, rather than reading its storage fields.

source
Treebars.initialize_progress! Function
julia
initialize_progress!(kind::Symbol[, N]; description="Running...", kwargs...)
initialize_progress!(parent::ProgressNode[, N]; description="Running...", transient=false, kwargs...)

Create a root from a backend symbol, or a child of an existing node. Return a ProgressNode; return nothing for a disabled parent. :state is built in; :term requires Term to be loaded.

An integer N creates a determinate counter. Omit it or pass nothing for an indeterminate node. Pass it positionally or by keyword, not both. transient=true detaches a finished child; failed children remain attached. Unsupported argument shapes and unloaded backends raise ArgumentError.

Use with_progress for application work so finalization and failure are handled on every exit. Direct initialization is useful for backends and nodes whose lifecycle is owned by a replica.

source
Treebars.update_progress! Function
julia
update_progress!(node, i; kwargs...)
update_progress!(node, message::AbstractString; kwargs...)
update_progress!(node, note::TreebarNote; kwargs...)

Update progress on node. Pass an integer to set the counter, a string for a status message, a TreebarNote for a message written in the page's language (treebar_notes), or keyword arguments to create/update labeled child nodes. No-op when nothing.

See @progress and with_progress for wrappers that handle the full initialize/update/finalize lifecycle automatically.

source
Treebars.prepare_progress! Function
julia
prepare_progress!(parent, args...; kwargs...)

Create a child progress node in the pending state — appears in the tree but not yet started. Call start_progress! to transition it to running. Used by @progress begin … end to pre-enumerate phase markers. Takes the arguments of initialize_progress!, including the counter total (prepare_progress!(parent, 5; …) or prepare_progress!(parent; N=5, …)).

source
Treebars.start_progress! Function
julia
start_progress!(node)

Transition a pending progress node to running. Idempotent; no-op for backends without a pending concept.

source
Treebars.finalize_progress! Function
julia
finalize_progress!(node; kwargs...)

Finalize a node without overwriting an existing failure or reuse state. No-op for nothing. Prefer with_progress to pair work with cleanup.

source
Treebars.fail_progress! Function
julia
fail_progress!(node; kwargs...)

Mark a progress node as failed. No-op when nothing.

source
Treebars.skip_progress! Function
julia
skip_progress!(node)

Terminate a pending progress node as skipped — it was pre-enumerated but never entered, and never will be (control flow left the block first). Distinct from finalize_progress! (which means "ran and completed") and from fail_progress! (which means "ran and threw").

Idempotent, and a no-op on a node that is not pending: a running node has started, so it is finalized or failed on its own terms, never skipped. No-op for backends without a pending concept.

source
Treebars.reuse_progress! Function
julia
reuse_progress!(node)

Mark a pending or running phase reused because its result already exists. A reused phase is terminal and distinct from finished or skipped. Before entry it has no duration; after entry it retains time spent checking the result. Later finalization preserves reuse; a later exception can still fail it. Pending children become reused and running children are finalized.

Idempotent on terminal nodes. The text view uses ↺; the HTML view and phase_overview have a reused group. Backends without this state, including Term, finalize instead. No-op for nothing.

source
Treebars.add_child! Function
julia
add_child!(parent, child)

Attach child as a child of parent. No-op when either argument is nothing, which makes it safe to use with optional/disabled progress trees.

source

State queries ​

Treebars.is_pending Function
julia
is_pending(s)

true when a progress node has been created (via prepare_progress!) but not yet started and has not been terminated — i.e. it is still expected to run. Defined on StateProgress and on ProgressNode{<:StateProgress}; false for backends without a pending concept and for nothing.

A node that was pre-enumerated and then bypassed is is_skipped, not pending — see the state table on StateProgress.

source
Treebars.is_running Function
julia
is_running(s)

true when a progress node has been started (via start_progress! or an eager initialize_progress!) and not yet finalized or failed.

For backends without lifecycle timestamps (e.g. Term.jl jobs), answers from the backend's own running flag instead — see isrunning.

source
Treebars.is_finished Function
julia
is_finished(s)

true when a progress node ran and was finalized successfully (via finalize_progress!). A node that never started is is_skipped, not finished, and a node whose result was reused is is_reused.

For backends without lifecycle timestamps, true when the node is neither running nor failed — see isrunning.

source
Treebars.is_failed Function
julia
is_failed(s)

true when a progress node has been finalized as a failure (via fail_progress!).

false for backends without a failure concept (e.g. Term.jl, which neither records nor displays failure): a failed Term node reads finished, so check for the propagated exception instead.

source
Treebars.is_skipped Function
julia
is_skipped(s)

true when a progress node was pre-enumerated but never entered, and never will be — control flow left the enclosing block (an early return/break, or an exception raised in an earlier phase) before reaching it. Set by skip_progress!.

Distinct from is_pending ("will run, hasn't yet") and from is_failed ("ran and threw"): a skipped node has no duration, no error and no started timestamp. false for backends without the concept and for nothing, so a Term/disabled backend is unaffected.

source
Treebars.is_reused Function
julia
is_reused(s)

true when a progress node's result was already available, so the work it stands for was not done — a cache hit, or output prepared by an earlier run. Set by reuse_progress!.

Distinct from is_finished ("ran and completed") and from is_skipped ("never entered, and its result does not exist"): a reused phase is a success whose output exists. It has a duration only when it was entered before being marked reused. false for backends without the concept (Term.jl, where reuse_progress! finalizes instead) and for nothing.

source
Treebars.is_displayed Function
julia
is_displayed(node) -> Bool

Whether a node is allowed to render. An explicit displayed=false makes it transparent: its children render one level up, while its lifecycle still runs. Unset and explicit true both return true. With no explicit preference, a bare wrapper without a description, message or counter is also inlined by the renderer. Set displayed=true to show such a wrapper.

source
Treebars.duration Function
julia
duration(s)

Elapsed wall-clock time for a progress node as a Dates.Period. Returns Millisecond(0) for pending, skipped, or never-entered reused nodes; for running nodes counts up to now(); for finished/failed nodes, and reused nodes that were entered, returns the frozen finalized_at - started_at.

source
Treebars.eta Function
julia
eta(s)

Estimated wall-clock time remaining for a determinate, running progress node, as a Dates.Period, or nothing when no estimate is meaningful.

A node qualifies only while it is is_running with a known total (N) and at least one but not yet all steps done (0 < i < N); the estimate is the linear extrapolation elapsed * (N - i) / i (the same formula the Term backend uses for its ETA: column). Every other node — indeterminate (N === nothing), pending, skipped, finished/failed, or a node still at i == 0 (no rate yet) — returns nothing, so a renderer shows an ETA only when one exists. Read under the node's lock like duration (both render paths already hold it).

source

Interrupts ​

Treebars.request_interrupt! Function
julia
request_interrupt!(node) -> node

Request cooperative interruption on this node and its descendants, including children created later. Siblings and ancestors are unaffected. This does not throw or change lifecycle state; work must check interrupt_requested or throw_if_interrupted.

The request is thread-safe, idempotent and persists for the node's lifetime. Target the job subtree rather than a long-lived root. No-op for nothing.

source
julia
request_interrupt!(mirror::ProgressMirror, id) -> mirror

Request an interrupt on the node of mirror's tree that has id in its frames: the id a replica's on_interrupt handed over (see progress_replica). Unknown ids, such as a node that has since left the tree, are ignored. The node is looked up in the tree: a viewer's Stop can afford that, and it spares every node of the run an index entry.

source
Treebars.interrupt_requested Function
julia
interrupt_requested(node) -> Bool

Whether an interrupt was requested on the node or an ancestor. Return false for nothing. Call at a point where the work can stop; use throw_if_interrupted to abort by exception.

source
Treebars.throw_if_interrupted Function
julia
throw_if_interrupted(node) -> nothing

Throw ProgressInterrupted if interrupt_requested(node), else return nothing — the one-line opt-in for work that aborts. Under @progress / with_progress the exception fails the node like any other error. A runner that should instead stop cleanly (finish its node, keep a partial result) checks interrupt_requested and returns. No-op for nothing.

source
Treebars.ProgressInterrupted Type
julia
ProgressInterrupted(node)

Thrown by throw_if_interrupted when an interrupt was requested on node or one of its ancestors. node is the node that was checked.

Resource acquisition ​

Treebars.with_busy_retry Function
julia
with_busy_retry(parent, acquire; policy, description="Waiting for resource",
    transient=true, sleeper=sleep, clock=<monotonic clock>, random=rand) do value
    ...
end

Acquire an explicitly busy resource with bounded exponential backoff and jitter. acquire() must return either ResourceBusy or ResourceAcquired. Only ResourceBusy is retried; acquisition exceptions and invalid results fail immediately.

Treebars creates one child progress node and reuses it for every busy attempt. Its message reports the busy reason, retry number, and delay. On acquisition, the message is cleared and the child is finalized before the consumer body is called, resetting the backoff lifecycle immediately. A transient child (the default) therefore disappears on success but remains visible with an exhaustion summary when it fails.

The consumer body owns use and release of the acquired value. Its exceptions propagate unchanged and do not trigger acquisition retries. sleeper, clock (seconds), and random (a sample in [0, 1)) are injectable deterministic test seams.

This helper is for explicit resource-busy acquisition only. It does not alter Treebars' fixed HTMX, WebSocket, or terminal progress-polling cadence.

source
Treebars.BusyRetryPolicy Type
julia
BusyRetryPolicy(; initial_delay=0.5, multiplier=2, max_delay=8,
    jitter=0.5, max_retries=nothing, max_elapsed=nothing)

Policy for with_busy_retry. At least one bound must be supplied:

  • max_retries counts retries after the initial acquisition attempt. Thus max_retries=6 permits at most seven acquisition calls.

  • max_elapsed is a wall-clock budget in seconds. A retry whose delay would exceed the remaining budget is not started.

The nominal delay grows by multiplier up to max_delay. jitter selects a uniform lower range: the actual delay is between (1-jitter) * nominal_delay and nominal_delay. Set jitter=0 for deterministic delays.

source
Treebars.ResourceBusy Type
julia
ResourceBusy(message="Resource busy")

Explicit result from a resource-acquisition callback passed to with_busy_retry. Only this result is retryable; thrown exceptions and other return values are treated as non-retryable failures.

source
Treebars.ResourceAcquired Type
julia
ResourceAcquired(value)

Explicit successful result from a resource-acquisition callback passed to with_busy_retry. value is forwarded to the consumer body.

source
Treebars.BusyRetryExhausted Type
julia
BusyRetryExhausted

Typed exception thrown by with_busy_retry when a busy resource reaches its retry-count or elapsed-time bound. attempts counts all acquisition calls, including the initial call, and last_message is the last ResourceBusy message.

Formatting ​

Treebars.short_duration Function
julia
short_duration(dt::Union{Dates.CompoundPeriod, Dates.Period}) -> String

Format a duration using seconds below a minute and the two most significant canonical parts for longer durations. Subsecond values below 100 milliseconds retain millisecond precision; longer subminute values use tenths of a second, truncated rather than rounded.

source
Treebars.short_string Function
julia
short_string(x; sigdigits=2) -> String

Format values for progress messages. Numbers use significant digits and abbreviations at large magnitudes, with the same rules for integers and reals. Negative values retain their sign. Below abbreviation thresholds, integers are unchanged. Non-finite values pass through.

Containers forward sigdigits to supported elements. Long vectors show their first and last elements; pairs and named tuples retain keys. A Fraction formats as a percentage. sigdigits must be positive. Extend this function in a consuming package for domain-specific values.

source
Treebars.round2 Function
julia
round2(x)

Round x to two significant digits. Integers are returned unchanged. Tuples, named tuples, and arrays are mapped element-wise. missing and String values pass through.

Used as a building block for short_string; useful directly when preparing label values for update_progress!.

source
Treebars.Fraction Type
julia
Fraction(value)

Marker wrapper that makes short_string render a number as a percentage (Fraction(0.95) |> short_string == "95%"). Useful for things like acceptance rates in progress labels. Comparison and equality forward to the underlying value.

source
Treebars.ByteSize Type
julia
ByteSize(n::Integer)

A byte count for a progress note's {placeholder}. English writes it as "512 B", "850.0 KB", "26.9 MB" or "1.2 GB" (powers of 1024, one decimal); other languages use their decimal separator ("26,9 MB").

source
